## 实际修复

| 问题 | 原因与改动 | 证据与限制 |
|---|---|---|
| 不同资料根之间的进程归属混淆 | 旧扫描只按 bottle ID 等环境标记归属，两个 CIDER_HOME 的同名瓶子可能混入 UI、CLI 或备用门禁扫描。改为瓶子 ID 与当前配置的完整 prefix 共同匹配；拒绝被替换的瓶子符号链接、非绝对路径及坏字符串。GUI/CLI 使用各自 BottleStore 的同一映射 | 定向边界测试和实际 `ps --all` 均通过。没有向其他资料根的进程发送信号；不宣称环境标记构成抵御同用户恶意进程的安全边界 |
| 真实启动期间停止失败或进程已退出却报告失败 | wineserver 控制/等待客户端被误当成仍运行的服务器；启动中会出现晚到后代；exec 会使旧 audit token 代际失效；同步退出跨过截止点后缺少最后一次只读确认。改为排除控制客户端、反复捕获本瓶进程、刷新并校验真实 Mach 身份、保留未知状态、在截止时作延迟只读确认 | 实际正常启动后停止、启动中立即停止、两次停止后重开通过。停止失败时记录 prefix 对应的进程与错误信息；停止并非硬实时 watchdog |
| 首次直接调用 waveOutOpen 死锁 | 旧 0008 补丁中，StartDevicesThread 持有 g_devthread_lock 等待 worker；worker 的设备 InitOnce 发布又获取同一把锁。已有先查询元数据的测试绕开了冷启动路径。0014 将初始化移至获取启动锁之前，移除 worker 的重复初始化，保留真实设备、格式、错误码和 worker 的 COM 环境 | i386/x86_64 两个真实 Wine 窗口与首次音频输出均通过，确认实际加载候选模块。没有关闭输入、伪造设备能力、改同步模式或以成功空桩代替实现 |
