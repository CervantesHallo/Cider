| 问题 | 实际修复 | 验证 |

| P2：CLI 退出后，八个长期等待继续占满执行位置 | Broker 通知 GUI 解除观察；GUI 的 run --wait 将解除观察传给 WineRunner/Spawn，释放等待工作。已经启动的程序继续运行，自有子进程交给共用非阻塞回收器；不使用 Task 取消去停止整个瓶子。请求 ID 保留，提前到达的 detach 也留有界记录，防止迟到执行 | 八个原生观察者退出后新命令恢复、重复 ID 拒绝；真实产品中结束 CLI 后 Wine 仍存活、ps 可见、新命令返回 0；自有子进程自然退出后无僵尸 |
| P2：Bridge 重启后容量归零，GUI 仍满载却继续排队 | GUI 独立保存实际工作数量，跨连接保持普通 8 / 控制 2 的容量。不可安全取消的安装等操作继续占位到真实完成；结果回复前释放已完成位置。旧连接的输出不能借新连接继续发送，断线/解除观察唤醒 ACK | 八个不可取消夹具工作跨重连保持，新请求立即收到 GUI 的容量拒绝；显式释放后恢复；旧 ID 不重放，控制通道和健康慢读仍可用 |
| P2：同一 App URL 的另一个 CIDER_HOME 无法冷启动 | 原 NSWorkspace 默认复用目录 A 的 GUI，导致目录 B 约 15 秒后失败。新增规范资料根对应的持久 flock，冷启动前再次握手；没有当前根的 host 时明确创建新应用实例。仍核对精确 App URL、根及签名身份 | 旧二进制真实失败负对照保留；新版本 A 的四个并发冷调用、A 运行时 B 的三个并发冷调用、B 暖调用、返回 A 暖调用均通过，每根恰好一个 host，A 未被接管或关闭 |

## 保留能力、代价及回退

原 CLI 命令、参数、cwd、环境、输出、退出码及等待能力保留，执行者仍为真实 GUI；没有恢复 CLI 本地派生或增加游戏帧 RPC。断线只解除观察，不将执行结果伪报成功，也不自动重试。协议增加 detach，版本升为 2，App/CLI/Bridge 必须成套更新。

带观察令牌的 CLI 等待使用 50ms 非阻塞状态检查；只有遗留自有子进程尚未退出时，共用回收器才以 200ms 检查，不为每个断开的终端保留一个阻塞线程。普通 GUI/安装等待的默认调用保持原方式；未测整体 CPU、音频延迟或游戏帧率，不作性能提升保证。回退应成套撤回协议、GUI/CLI 和等待传递，不混装版本。

## 验证和证据边界

- 3 项自有子进程/观察单元测试通过：真实退出码 37、解除观察后仍存活并在后来被回收、单调解除状态。
- 5 项原生 NSXPC 定向检查通过：八个断线观察者释放容量、重连后 GUI 保留容量、已有 Bridge 崩溃不重放、保留控制容量、读者暂停六秒后完整输出。最终源摘要在各运行期间稳定，夹具进程和 job 清理通过。
- 4 项真实 release CLI/Bridge→只读 AppKit host 多目录检查通过，包含 9 次 CLI 调用；这些不是产品 GUI 或 Wine。旧二进制的负对照和早期夹具/清理失败及后续真实清理均保留。
- 另有一次真实产品 GUI→Wine 解除观察验收：GUI PID 34175 为 Wine PID 34217 的原生父进程，结束等待 CLI 后 Wine 继续运行，新的 engine list 返回 0，ps 仍列出程序；最后用正常整瓶停止清理。两项启动/空瓶准备另记，没有冒充额外功能验收。
- 首次产品清理将 lsregister 的 -10814 当成失败。独立查询确认精确私有引擎 App 路径根本未登记；进程/job 均已退出。原失败回执保留，最终交接引用其 SHA 和真实缺席检查。通用 bundle ID 与其他引擎共享，未按该 ID 注销其他路径。
- 最终显式声明回收器闭包的 self 捕获，消除 Swift 警告；再次通过上述 3 项单元测试，release 构建无编译警告、严格签名通过。**三个最终发布组件与前述真实产品运行所用组件逐字节相同**，因此没有再跑一次相同运行场景。初始警告日志也保留，日志中的编译器上下文空白不是源码空白修复对象。

源码/夹具/原始结果在隔离分支 `tests/runtime/product/`、`tests/xpc/`，汇总见 [结构化证据](evidence/quarantine-observation-closure-20261016.json)。没有请求摄像头/麦克风或取得 TCC 对话框、正式 Developer ID、Windows kernel 或新游戏会话证据。
