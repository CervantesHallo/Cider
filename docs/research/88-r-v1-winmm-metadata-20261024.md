# Engine R v1：WinMM 元数据与默认设备通知

日期：2026-10-24。原音频主题迁移，承接 86–87。当前是独立候选，不选入正式配方，不借旧引擎的游戏、媒体、小时或性能结果。

## 为什么需要语义迁移

固定新基线已经去掉旧版初始化时的共享格式探测，并改用新的格式映射路径。因此旧 Cider0008 不能逐字套入，0014 所依赖的初始化发布锁也需要按新布局重建。本轮只迁移设备元数据、失败清理、通知与启动次序；旧按需格式探测和新基线能力掩码的等价性仍单列待验。

源码中确认了未检查单个端点初始化结果、缺失默认设备时映射可能越界、通知与设备表发布顺序不完整等问题。第一版源审进一步给出四个 P2：失败回滚与未门控查询的交错、枚举与订阅之间漏通知、重排后的通信设备索引、成功初始化但没有 DebugInfo 的临界区。后续复审又核对了实际 MMDevice 提供者，而没有假设注册返回就代表监视已启动。

## 候选实现

- `0008-winmm-stage-device-metadata-before-worker.patch`：双方向设备表局部暂存；失败不发布，完整回收；缺失默认值保留全部端点；按不透明端点 ID 匹配，而不依赖两个 COM 包装指针相等。通信设备按稳定身份在最终映射中定位。
- 注册通知后才采样；初始化中的通知只推进变化序号。提交时在同一锁内复查序号，一次发布完整表；有变化则清理并留待下一次 InitOnce 重试。发布后没有注册失败再释放已公开表的回滚路径。
- 实例 ID、首个输入／输出偏好查询接入同一 InitOnce；启动工作线程前完成初始化，避免持启动锁等待需要发布锁的线程。
- 新基线的临界区可以在 DebugInfo 分配失败时仍返回成功。本候选显式删除已初始化的锁，再回收 ID 并返回失败，维持其余 WinMM 代码要求的前提。
- `0009-mmdevapi-arm-effective-default-notifications.patch`：通知线程先开启注册表监视，再采样初始角色；注册在通知锁外等待有界就绪。状态与句柄由引用计数保护，失败不伪造注册成功。每次唤醒先重新监视再读取，比较实际生效的四个角色 ID，覆盖通信默认设备隐式跟随普通默认设备的情况。
- 初始化采样失败真实返回。已就绪后的采样最多尝试三次，间隔 50／100ms；部分 ID 释放清零，旧完整快照保持。持续失败后仍保留监视，等待下一次变化，不因一次临时内存失败让已有订阅永久失效。

角色允许分别指定；ID 应视为不透明标识。[设备角色](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-roles)、[通知接口约束](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient)。本次没有通过解析 ID 内容猜测设备，新增通知路径也不从回调中注册或注销。

## 取舍与回退

收益是消除未完成表的暴露、漏掉初始默认变化和错误通信映射。代价是首次注册最多等待 5 秒就绪，新增每个提供者状态／事件的所有权，以及每次配置变化读取四个有效角色；这些不是音频缓冲区热循环。超时或准备失败仍真实失败。三次恢复全部失败不会补造 ID，且不承诺没有下一次事件时自动无限恢复。

候选只在受控私有引擎和空瓶中验证。原 v0、F27 原始产物、用户引擎及瓶子保留；回退为不选择这两项候选，并保留全部失败记录。正式采用还需要受影响真实运行、通知生命周期／失败路径证据，以及仍未通过的完整 M1 门禁。

## 已有证据与范围

两个模块均双 PE 完整组件编译零诊断，独立输出链接、补丁精确重建；canonical 源和原 DLL 未覆盖。WinMM 修复及提供者的限定源审分别记录，审查者不为未查看的运行结果背书。

原生夹具直接提取准备源码的函数体，使用明确的 COM／分配器依赖替身；源、harness 和 include 均固定到单次输出目录。两个宿主架构的最终组合各完成 93 个场景，覆盖依赖／分配失败、空枚举重试、通知期间快照变脏、通信重排／隐式跟随与显式固定、临时及持续采样失败。大量检查计数包含分配红区检查，不当作 Windows API 数量。它不验证真实 COM、CoreAudio、线程就绪竞争、InitOnce 并发或 DLL 卸载。

对夹具的复审修了源摘要绑定和订阅身份两项误报通过风险；初次负例驱动预期较晚的失败点，而实际更早拒绝，原回执保留并离线校正，没有重复运行挑结果。

末次复审补上连续部分失败的 oracle：先分配多个 ID 后失败，下一次在更早位置失败，分别核对恢复与耗尽；每次失败后四个输出均须清零。故意删除 reset 的真实原生负例在两宿主架构均被重复释放检查拒绝，最终限定源审无具体 P1/P2。ERole 替身也保持真实 0／1／2 常量，不将 Multimedia 与 Communications 合并。

共享运行器新增的中断清理缺口已经修正。真实自有程序以唯一标记确认存活后发送 SIGINT，失败状态 130 保留，GUI 内核退出、两次空观察和无残留均确认。首次控制器错误地把 list 模式中的活跃 PID 当作未知 pending 而提前停止；其救援清理及失败原件保留，修正后才取得目标结果。

真实 WinMM 冷入口已经执行：PE32／64 分别以输出设备打开、实例 ID 查询为首个入口，共四次，每次 39 项检查零失败；各自随后四个并发 mixer 元数据调用及退出均正常。core、EXE、运行器、四个新 PE 模块在引擎和前缀中的摘要、唯一会话、时钟及 GUI／Wine 清理均核对。没有提交声音缓冲区或打开输入流，不记为可听音频、麦克风或游戏验收。

提供者与运行器当前限定复审无具体 P1/P2。真实默认角色变化、通知线程延迟／失败并发、现有回调持锁重路由的非阻塞契约及 DLL 卸载仍待各自验收；不能用这些四次冷入口或旧 v0 的 WMA／mixer 结果替代。结构化归档见 `evidence/engine-r-v1-winmm-metadata-20261024.json`。
