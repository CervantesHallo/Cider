# R v1：同一宿主的两个真实生产者独立回收

2026-11-01，UTC+8。接续[127](127-r-v1-cross-pixel-20261101.md)，按原两／三进程顺序，实际创建一个host和两个producer进程。host拥有同一Root下两个不同childslot；每个producer独立创建真实context、lease/ticket、RO读方、Metal队列与两色帧。

两位宽方向均通过：host142项／0失败，两个相反位宽producer分别35项／0失败，CLI0、两次实际kerneljoin及exit0，无强制。两个模型同时为1后才分别回复；B已提交蓝帧并持有资源时，延迟B的第二次回复，让A实际取消、取得SAFE、GPU drain、释放context／RO、正常退出并归还host观察引用。之后首次新读B的第二阶段，实际模型仍1、context／读方持有、producer仍运行；再允许B取消及完整退出。没有重复probe序号、代造回复或用进程退出替代资源安全许可。

诊断host观察方从单槽扩为固定两槽，以准确Root＋child区分，不在本轮复用槽位。首次绑定另核对普通coordinator真实child、context、ticket、producer PID/birth与lease，两个槽各持有一个窗口引用并独立释放；producer与普通coordinator／Metal实现不改。限定Native／客户端增量源审均无P1/P2，NDEBUG、双PE严格编译与匹配Unix9/watch2通过。

首方向程序已完整通过，但两个producer的首条完整JSON被并发stdout拼在同一行，旧逐行判定器报Extra data。原failed控制器／raw保留；新判定器严格消费相邻的完整JSON对象及全部尾部，不修字节、不丢记录或忽略坏尾，并重新核对每个PID完整检查序列，只重判原raw。随后只运行缺失反向。该现象说明单次fwrite不保证跨进程JSONL行原子性，不将它当日志原子性保证。

9组有效编译依赖闭包、236项项目输入、两个实际EXE／16PE／2Native／F27、原raw/session、7份实际GUI/kernel清理、原瓶配置DLL字节或缺失恢复及四保护摘要，以1430项独立检查另行绑定。两次host约4.1／2.8秒，不作为性能比较。五文件诊断补丁逐字重建；见[源码](../../tests/graphics/three-pixel/)和[证据](evidence/r-v1-three-pixel-20261101.json)。
