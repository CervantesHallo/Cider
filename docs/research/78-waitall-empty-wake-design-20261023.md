# WaitAll：减少空事件唤醒的设计审查

状态：F22/0118 已实现、独立源审、组件构建和短功能验证通过；固定六轮性能两项失败，不采用、不跑自己的小时。接续原 02 的 M1；HY 顺序、Windows 状态、用户引擎与游戏门禁不变。

## 已确认的依据

F21 自己的短功能通过，六轮正式性能只有 4.50 倍，控制 +41.1765%，均失败。隔离原生诊断显示取消状态切换和空 ulock wake 值得继续查，但不能据此归因实际 Wine。随后保留原 guard 的真实 Wine 诊断完成：msync 报告 198674 帧进入时为 ENABLE、DISABLE 为零；两种后端报告的请求 QoS 均为 21，不代表实际调度或 core placement。

不采用永久禁用 POSIX 取消来追数字：它会改变 frame 外行为，Apple 返回 runloop 的注册及外部回调线程也不能当作 Wine 独占线程。此候选保留原有 disable/save/restore、控制信号、pins、事务与死亡恢复。

当前 `multiple_waiters` 是服务器维护的 **Mach 登记计数**，不是可借用的布尔位。不能打包或覆盖它。外部资料通道本轮不可达，以下设计来自已固定的本机 Wine/Cider 源码审查，不声称已对照新 Linux 实现。

## 范围与成本

只考虑 `MSYNC_AUTO_EVENT` / `MSYNC_MANUAL_EVENT` 的空 ulock wake。其他类型保留原 always-wake，恢复通知始终保守 wake。Mach 登记、通知及其计数保持。

在协调文件 epochs 后追加 65536 个 uint32 提示桶：`bucket = shm_idx & 65535`。新增 262144 字节共享映射，总大小拟为 134545408 字节；不是追加 1 GiB 的精确索引表。实际驻留、文件 blocks 与页表成本仍须测量。

桶计数是保守的“可能仍会进入单对象 ulock 的调用数”，不是内核等待者数或引用数。碰撞、SIGKILL 遗留和饱和只使更多通知退回原 always-wake；不改变许可、对象寿命或 Mach 节点。计数 UINT_MAX 后永久 sticky，增减都不再改变它，避免回绕为零。

代价还包括通知中的提示读取/显式 fence、实际阻塞事件的登记/撤销及少量 native 栈空间；不能把退回旧路径说成与旧路径耗时完全相同。已知零超时轮询不登记或设置 sticky；非零超时若在随后过期，仍须正常撤销。

只在新协调实例初始化零。**对象槽复用不能清桶**：其他对象可能落在同一桶。两个 native 与服务器必须匹配新 magic 7 / 新文件大小；旧版本拒绝映射。现有 16 字节对象槽不改。

## 必须满足的顺序

1. 原 owner 下检查未就绪，确定是否真的将进入 payload 上的单对象 ulock。必须覆盖 WaitAll 选出的 blocked object，不能只看 `count == 1`。
2. 普通已 pin 的事件，在 owner 内增加桶计数并发布本线程 native 栈登记；在释放 owner、允许控制信号或进入内核前，两项均须完成。TLS 地址预先在 owner 外取得。
3. 计数持续存在，直到内核等待已返回，或原退出 unwind 确定该调用不再恢复。正常、超时、错误路径都恰好撤销一次；撤销在原 control 保护下，先于 caller pins 释放，不要求已退休 epoch 再次准入。
4. 借用 alert 等未证明同等 pin 寿命的单等待，在非零超时路径无条件将对应桶设为 sticky，即使当前类型不在优化范围。这样覆盖离开 owner 后槽类型变化的情况；不能用槽复用时清零来补救。
5. fork child 仅清继承的 TLS 登记头，不扣父桶；parent 保持原登记。原 quiescence、lease 刷新及 retired/exec/`_exit` 约束不变。
6. 通知者和旧 helper **永不清桶**。正常 owner-held 通知，仅当普通事件桶为零才跳过该 ulock syscall；恢复/阻塞通知始终 wake。
7. 跳过 syscall 后，payload 发布到读取 Mach 登记计数之间仍须有明确 Store→Load 屏障，例如 SC fence。单等待依赖 owner 的发布证明，Mach pump 不取 owner，不能混用两者证明或依赖原 syscall 的隐含效果。

### 关键反例

W1 登记后尚未 park；SetEvent 置 1，W2 消耗成 0；W1 迟到进入 ulock。W1 的桶计数仍在，下一次 SetEvent 必须 wake。若通知者交换清桶，会在这个 ABA 时序丢掉后续通知。

注册不能随意移到 owner 外：payload store 与提示读取之间的重排可能让通知者看见零、等待者却仍比较到旧 payload。退出后也不能凭对象索引重建“新登记”去扣减，必须使用原调用发布的稳定桶登记。

- 新 header 的既有事务恢复/负例必须重新核对；不能借旧版本 header 结果。
- 匹配的客户端/服务器/统计读取器构建，两位宽短功能、生命周期、线程和多进程验证通过；原超时与失败记录保留。

## 实际实施与验证

独立实现复审发现一项 P2：内部 count0 借用 alert 路径若仅对当前普通事件设置 sticky，离开 owner 后槽类型变化会触发进程级登记断言。已改为非零超时无条件 sticky；复审确认该项闭合，无其他具体 P1/P2。零超时仍不登记；原 Mach 计数字、16 字节槽及 POSIX 取消边界保持。静态复审不能代替运行证明。

最终 native pair 为 ntdll `c9d5ec1492b83cba1da7db82caff3702e0512d42a186c947dea7cceefb89a0fa`、server `f505306279fa036d1c2ffdbac260242214e737fb3f44881cd35c8fa4577cbcd0`；SDK15.4/O2 构建零警告，补丁三文件精确重建。构建初期和修正前的哈希、失败回执分别保留，没有追认旧二进制通过。

- 生产 magic7 header 的原生协调恢复夹具在 arm64/x86_64 通过；新提示夹具两架构通过碰撞、正常收支、吸收式饱和、fork、SIGKILL 保守残留及实际 ulock ABA。明确观察目标线程 kernel park。
- 五个 x86_64 负对照均拒绝：清桶、漏登记、子进程扣父计数、饱和回绕及旧 decrement 覆盖 sticky。前两个实际 ABA 等待超时；没有把失败用例作为引擎候选运行。
- 自己的 11 阶段 Wine 验证通过，九份 driver 记录逐一匹配实际 native pair 与两位宽 PE 哈希；包括原基础、生命周期、8 线程、四进程和 20 秒压力，以及子启动拒绝 1260。
- 新增单事件生命周期在 PE32/PE64 各 64 轮通过，各 2179 项检查、128 个线程创建/回收、64 次暂停/读上下文/恢复/终止，以及 64 次重新唤醒。保留同一个 manual-reset subject；ready/live 只证明公共 API 阶段，不证明内部等待登记。原生 ABA 证据与它分开记录。
- 统计读取器严格核对新文件格式；提示字段明确非一致全局快照。后台进程仍可能有正常等待，不能把非零桶直接认定为泄漏；SIGKILL 残留只保守增加唤醒，不增加对象引用。实际资源成本仍待专门观察。

原固定六轮、同 native pair、v4 EXE、250000 次/4线程对照完整结束：server 唤醒中位 10100ns，候选 2800ns，3.607142857 倍未达 5；私有 CS 为 1.379/1.252ns/op，偏差 −9.209572%，未达 ±3%。不以最后一轮更快来替换整组中位，不重试挑样，不借旧小时。不能单凭这组结果归因 CPU、后台负载或单个实现步骤；它只表明该队列未达到接受门槛。

另作两个串行的资源观察会话，同一 x64 EXE/64轮，分别为 F21/F22；它们不参加性能统计。实际目录文件大小分别见 134283264/134545408 字节，新格式最大已分配 blocks 为 344064 字节，对照旧格式 81920 字节。F22 目录还保留旧模板文件，不能把所有目录文件当活跃映射。总进程 RSS 采样约 1.16–27.39MiB / 1.48–26.22MiB，生命周期时间点不对齐，不能从差值宣称提示区节省或新增了多少驻留内存；新增虚拟区明确为 256KiB，独立页表/RSS增量仍未归因。两次新生命周期均通过，最后确认私有 GUI 退出及连续两次无自有 Wine 进程。完整资源原始记录、提示字段和失败性能队列保存在同一证据索引中。

## 后续实现约束

独立只读复审否决了直接用 `pthread_cleanup_push/pop` 替换每帧 disable/restore：pin 增加与发布、移出帧与最终释放、frame链与计数、owner/admission之间都有非原子窗口；清理回调不自动修复这些窗口，fork等待与FD清理还可能互相阻塞。父代理核对了这些源路径。此替换没有实施。

后续拟从F21原保护边界尝试普通事件的有界预等待轮询：固定最多64次，只读状态、不持owner、不消费许可，变化后仍重入原事务检查/获取，耗尽后保留原ulock与超时处理。它不包含F22提示桶，不改变Mach泵或POSIX取消。收益尚未测量；代价是短暂CPU轮询与可能的有限超时超调，不能承诺减少实际kernel wake成本。必须独立审查、运行和同门槛对照，不据此提升M1。

补充来源：后续网络读取已恢复，Apple的公开[取消实现](https://github.com/apple-oss-distributions/libpthread/blob/libpthread-539.100.4/src/pthread_cancelable.c)显示state更新会调用内核取消状态接口；[公开清理宏](https://github.com/apple-oss-distributions/libpthread/blob/main/include/pthread/pthread.h)只管理清理栈。公开版本不是本机已加载libpthread的二进制身份证明；原生成本和真实帧状态仍以本机原始记录为准。未读取或修改私有pthread取消字段。

## F23：有界轮询的实施
