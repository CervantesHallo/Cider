# K1/K3 实际 Wine 运行及分配失败清理续修

2026-10-17。用户继续要求修复全部隔离问题，保持原实现和方向。本轮沿用原对象管理器、IRP分派与回调架构，继续隔离实施；没有将K2未完成或真实Windows缺口改称完成。

## 两项新确认并修复的问题

### P2：CLOSE分配IRP失败时误释放借用文件

`dispatch_create`创建ref=0的FILE_OBJECT代理；服务端CLOSE请求持有其文件，`dispatch_close`没有取得一份本地Ob引用。旧OOM分支却解引用一次，0013的零计数检查会拒绝该操作，错误可能从分派路径展开。

0015仅移除该未配对释放，直接返回原STATUS_NO_MEMORY。保留零引用防护及服务端请求持有/完成协议，没有新增引用环或伪造成功。父代理独立核对`server/device.c:create_irp/set_irp_result`与分派路径；只读复审确认最小修正。

精确抽取修后函数，ASan/UBSan模型覆盖分配失败、正常分派、空文件三条路径，借用本地ref始终0。旧函数同OOM输入触发未配对释放断言。模型模拟IRP依赖，没有对实际Wine注入资源耗尽，不能称其真实异常回滚已全面通过。

### P2：IOCTL构造失败时释放context仍拥有的缓冲区

METHOD_BUFFERED输出可能直接别名输入，也可能扩容后成为context的新输入，旧输入留在to_free。旧失败分支无条件释放out_buff，context却继续保留该指针，后续复用/清理可能造成悬空访问或重复释放；扩容时旧输入还会泄漏。

0016只释放与context当前输入分离的输出，并释放被替换旧输入to_free；context仍拥有的缓冲保留给主循环。实际构造函数及IoFreeIrp不在这些失败点接管输入，因此无需恢复或捏造另一个拥有者。原STATUS_NO_MEMORY及成功路径均保留。

精确函数体的12条失败/成功路径覆盖别名、扩容、独立与空输出，真实宿主分配在ASan/UBSan下均恰好释放一次；旧相同路径重现ASan double-free。复审确认本处没有新的P1/P2疑点，未声称整个Wine所有OOM路径已审完。

## 实际运行推进

使用全新、无账户私有前缀和引擎代码副本，实际产品CLI→XPC→GUI完成初始化。只替换该副本中32/64位ntoskrnl PE为组合0009/0012/0013/0015/0016产物，原生wineserver、loader及其门禁绑定字节保持；0009的server/token.c未部署。因此本运行明确只覆盖通用事件/对象与回调，不覆盖token映射或K2。

自有Wine客户端创建唯一自有服务，装入自有无输入IOCTL夹具，完成：

- 每种架构256轮事件：取得真正引用、关闭原句柄、读取/设定/等待事件、最后释放。
- 每种架构64个真实线程池回调：回调自身先释放work item，外层仍正确清理捕获的device。
- 64轮含22次有序pin后关闭、21次先关闭负对照及21次实际关闭/引用竞争；成功引用保持对象可读，已关闭/复用的句柄允许真实失败状态。两类结果都必须实际出现。
- named driver引用及显式不支持的HandleInformation结果；后者的行为、模块摘要和loaddll轨迹一起约束实际候选路径。

最终x64及i386各1560项检查、0失败，服务STOPPED读回/删除成功，加载和卸载轨迹可见。i386实际加载syswow64的ntoskrnl和32位夹具；不是仅运行32位客户端调用64位服务。全部本批Wine/GUI/CLI/job清理通过。

这些是Wine实际用户态驱动宿主，不是Windows内核。没有测试游戏/反作弊或新增身份/访问通道。非native API的void失败契约、完整PnP/SEH/后端失败恢复及独立Windows仍分别欠缺；不能据本轮解除门禁。
