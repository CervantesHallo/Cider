# 09 米哈游三款 Windows 国服本地适配

> 2026-10-06 · 按用户最新目标修订。依赖 00 的 R3 / ADR-010、02 引擎、04 图形、05 应用、06 数据、07 平台集成；执行状态记入 13。本文是目标与待办，不是游戏已可玩的声明。

## 1 目标与验收

原神、星穹铁道、绝区零的官方 Windows 国服客户端在 Cider 中本地可玩，和柚子社全系并列为最终游戏目标。每款独立记录渠道、游戏版本、引擎构建、macOS、设备、图形后端与 CPU 后端。

最终验收覆盖：官方启动器安装/更新 → 用户自行完成登录 → 进入可操作游戏场景 → 渲染、音视频、键鼠/手柄与网络功能 → 正常退出并重新启动。基线要求每款至少三次独立会话、每次至少 30 分钟；记录崩溃、卡顿、帧时间、内存压力和已知缺陷。更新流程与重新启动单独留证据，缺项标为待验证。

安装器、启动器界面、下载完成、API 对照、预检和官方云分别验收。官方云用于当前不可用时的兜底；本地适配是否完成以游戏本体证据判定。具体硬件性能门槛在获得首份本地基线后制定，不从启动器帧率推算游戏性能。

## 2 工程取舍

用户允许为目标复议工程和产品约束。额外依赖、体积、实验后端、产品范围、开发顺序、UI 和部署形式可以形成具体候选方案。每项记录：要解决的问题、收益、代价、技术依据、采用状态、验收与回退。原有范围排除须明确改写对应决策后才进入实现。

忠实兼容工作实现真实的 Windows 行为，并如实表达实现范围和失败。不提供反作弊伪装、隐藏、欺骗或绕过，不以成功空桩冒充安全能力。

## 3 API 保真证据

`data/kernel/fidelity.json` 是对指定历史引擎树的审计；`severity` 描述所审计代码的状态，`disposition` 描述预期处置。加载器拒绝矛盾数据，不能替代引擎补丁，也不能证明该 API 已在 Windows 上做过对照。

每项后续工作提供：具体 Windows 契约、源代码位置与引擎版本、可实现范围、真实 Windows 对照、实现或明确失败、调用方行为与回归证据。涉及对象生命周期、并发和权限时一并验证。先修可独立证明的通用行为，再评估驱动运行时的依赖组合。

历史 `unreachable` 判定的范围限定为当时审计的架构。需要新的证据区分“当前缺少实现”“需要改变架构”和“该架构无法兑现契约”；无 ring 0 这一事实本身不等于所有 Windows API 或所有替代架构永远不可实现。复议须更新证据、矩阵修订和对应计划，不直接把条目改为已实现。

KMDF、安全 API、诚实失败码、Windows 对照与上游贡献、用户态保真修复继续按五项分别推进。仅加载驱动不代表安全能力齐全；仅让无法支持的调用失败也不代表本地游戏适配完成。

## 5 当前实现缺口与通过后的启用

2026-10-06 的有界代码审查确认以下缺口，作为 HY2/HY3 的输入：

| 位置 | 当前行为 | 计划交付 |
|---|---|---|
| `CiderData/Preflight.swift` / `CiderRuntime/WineRunner.swift` | `Preflight.check` 有 DB 与版本环境键接口，`WineRunner.launch` 实际固定传 `db: nil` | 采集真实渠道、版本、引擎与宿主环境，统一映射兼容证据；组件通过、待游戏验证、正式可玩各有明确状态 |
| `WineRunner.environment` / `cider/0001` | 无条件下发全部受限程序名，引擎仅按名称拒绝；未绑定通过状态 | 设计应用直启和启动器子进程一致的可信验证状态，绑定具体安装版本与引擎构建；先用自有普通程序验证未知/失配拒绝与匹配状态流转 |
| `KernelFidelity` / `data/kernel/fidelity.json` | 存在预期为 `honest_failure`、审计代码仍为 `deceptive_success` 的条目 | 引擎补丁、构建哈希、Windows 对照与失败行为分别留证据，处置意图和实际状态分开更新 |
| 三款 `cider.game/v1` 数据 | `verdicts` 均为空 | 原神先建立国服版本环境基线；通过后记录真实会话，另外两款独立完成同样流程 |

单项 API 对照通过只提升该组件的完成状态。实验环境进行游戏集成验证需要其依赖组合的兼容证据；正式启用需要对应游戏的实际会话记录。两者应在验证状态设计中区分，避免要求“先可玩才能启动、先启动才能验证”的循环依赖。设计在改变启动行为前评审，不能预置通过裁定或提供用户强制放行开关；游戏更新或环境失配回到待验证状态。

## 6 子代理与进度

默认主代理自己调研和实现；仅超大任务按窗口、图形、用户态 API、驱动契约或版本证据拆成具体独立研究或代码实现项，先开 1–2 个子代理。任务指定证据、产物和文件范围；主代理同时推进关键路径，复核并接入已完成结果。一个项耗时失控时保留产出、收窄问题，不重新发起整套调研。

实质变更先做对抗性审查，覆盖错误假设、误归属、并发与失败路径。执行状态统一更新 `13-roadmap.md`，实验失败和未知项同样记录。研究和成功运行的结论分别留证据，避免把计划或审计当成已完成实现。


## 7 本轮可行性结论与下一批实作（2026-10-06）

依据 [内核契约调研](../research/23-kernel-feasibility-20261006.md) 与 [窗口坐标调研](../research/24-winemac-frame-feasibility-20261006.md)，先落地 HY1 的可独立验证部分，再进行 HY2 的通用契约实验：

- KMDF 对象、请求队列、取消/完成等有公开契约与源码，可做有界运行时研究；依赖的 WDM 行为和对象生命周期须逐项证明，不能以加载成功验收。
- 同步进程/对象回调需要新的 wineserver 裁决协议，并验证重入、注销、失联与权限裁剪。现架构缺实现不等于所有架构永久不可行；实验也不自动证明宿主整体保护或游戏接受。
- 首批权限对照须同时覆盖 UserMode 与 KernelMode。微软契约规定 KernelMode 的权限成功分支，不能把全部 TRUE 判成伪成功或统一改 FALSE。先取得 Windows 基线与明确令牌语义，再改引擎。
- L5 先用独立 GDI 自绘窗口区分根装饰与远程 swapchain 的几何问题；确定的 style-mask 初始化缺陷单独修复。源码行号、坐标证据与候选处置见调研；按应用名去掉标题栏不作为验收。
- L6 实作按瓶子串行的启动/停止/重启；重复启动不新建实例；停止观察实际退出并检查子进程替换；信号前重查进程出生时间；启动器不拥有默认 `games` / `steamapps` 子库。对外部入口同时启动和任意应用目录布局的边界保留实测记录。

本轮采用的取舍是增加有界的退出等待与重新扫描，代价是停止稍慢，收益是避免把旧实例当重启和错误成功提示；可独立回退 AppLifecycle 与 scanner 修改。正式窗口补丁、驱动运行时、宿主特权组件、虚拟机及游戏集成启用均须各自证据后决定。本轮不计入三款游戏可玩验收。

本轮第一批实现、隔离窗口实验、审查修正及实机生命周期证据见 [research/25](../research/25-feasibility-implementation-20261006.md)。L5 候选补丁尚未进入用户引擎，三款游戏本体未验收。下一步仍按 HY1 → HY2/HY3 → HY4/HY5 执行。
